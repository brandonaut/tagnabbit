## Context

`src/cache/playerFile.ts` currently stores exactly one record, keyed by a fixed `"current"` key, holding `{ blob, name, type, position, balance, mono, speed }`. `PlayerPage.tsx` reads/writes this single record on load, on every scrub/balance/mono/speed change (debounced), and on unmount. See proposal.md - Why for the motivation to move to a playlist.

`src/cache/sheetMusic.ts` has a proven pattern for a *cache* — LRU eviction, byte budget, `localStorage`-tracked metadata alongside Cache-Storage-held blobs — but that pattern explicitly does not apply here (see proposal.md and the spec's "Playlist persistence" requirement: no automatic eviction, since a playlist is user-curated, not a cache).

The waveform, drag-to-scrub, tap-to-toggle, transport controls, tuner popup, and wake-lock behavior added in prior changes all operate on "whatever `<audio>` element is currently loaded" — none of them need to change; they simply keep acting on whichever track is currently active.

## Goals / Non-Goals

**Goals:**
- Replace the single IndexedDB record with a store of playlist track records, each holding just its audio file, name/type, and playlist order.
- Persist playlist order and a single global mono setting.
- Support adding multiple files in one action (picker + drag-and-drop), reordering via a pointer-based drag handle, and removing via swipe or hover-reveal, all without silent data loss beyond what the user explicitly removes.
- Keep position un-persisted and always reset to zero on track selection, per the explore-session decision.

**Non-Goals:**
- No automatic playlist eviction/pruning (contrast with `sheetMusic.ts`'s LRU cache) — this is user-curated storage.
- No cloud storage, drive/dropbox integration, or directory-handle memory — out of scope per the earlier exploration's device-coverage findings.
- No changes to the waveform, drag-to-scrub, tap-to-toggle, skip/timeline transport, tuner popup, or wake-lock behavior — they continue operating on "the active track" unchanged.
- No multi-track simultaneous playback (that's the separate, unrelated, not-yet-started `add-dual-track-player` scaffold) — this change is strictly "one track plays at a time, chosen from a list."

## Decisions

**Storage shape: one IndexedDB object store of track records, keyed by a generated track id, plus a separate small record for global state.**
`playerFile.ts` changes from a single `put(record, "current")` to an object store of records `{ id, blob, name, type, order }`, and a second tiny record (or a second object store) holding `{ mono, activeTrackId }` — global settings that aren't per-track. `order` is an explicit sortable field (not implicit array position) so reordering is a matter of rewriting `order` values, not restructuring how tracks are stored. Balance and speed are deliberately absent from this record — see the dedicated decision below on why they aren't persisted at all. Alternative considered: store the playlist as a single array-valued record (like today's one record, just now holding an array) — rejected because every reorder/add/remove would require reading and rewriting the entire array including every track's `Blob`, which gets expensive as the playlist and its audio data grow; individual keyed records let each operation touch only the record(s) it needs.

**Balance and speed are not persisted at all — reverted from an earlier per-track-memory decision.** An earlier round of this same change had each playlist track remember its own last-set balance and speed, restored on reselection (mono stayed global throughout). A later round of feedback reversed that: balance and speed now behave exactly like position always has — reset to their defaults (centered, 1x) on every track load, never written to storage. This removes `updateTrackState`, the debounced per-track persistence timer, and the `balance`/`speed` fields from the track record entirely, rather than leaving now-dead plumbing in place. Net effect: only `mono` (global) and the playlist itself (tracks + order) persist across sessions; everything else about a track's playback state is transient, reset fresh every time it's selected.

**Track identity: a generated id, not the file name.** File names collide easily (two different recordings both named `recording.m4a`) and aren't stable identifiers for "this specific row in the playlist" — needed for reordering, removal, and knowing which record is the persisted `activeTrackId`. Each add generates a fresh id (e.g. `crypto.randomUUID()`, already available in the browsers this PWA targets) at add time.

**Cold-restore behavior: restore the playlist and the last-active track's audio loaded (balance/speed reset to defaults, position zero), but paused — not autoplaying.** The spec's "Selecting a track from the playlist" requirement mandates autoplay only for an explicit user *tap*; autoplaying on a bare page load has no such gesture behind it, and browsers' autoplay-without-gesture restrictions would likely block it anyway (the existing single-file restore-on-mount flow already left the file paused for the same reason — this preserves that behavior, just for whichever track was last active in the playlist). The rest of the playlist is visible and selectable immediately; only playback itself waits for an explicit tap or the existing play button.

**Removing the active track falls back to the first remaining track, not the empty state — revised from the original decision.** This was originally "stop and return to the empty state, no auto-advance," rejecting fallback as an unrequested assumption. A later round of feedback established a stronger, explicit invariant instead: the playlist should never show "no track active" while it still has tracks. This is deliberately **not** the "auto-advance to next" behavior considered and rejected earlier — that would have meant "play whatever came after the one I just removed," a positional continuation assumption nobody asked for. The actual rule is simpler and doesn't carry that assumption: always fall back to the *first* track in playlist order, the same fallback used for a fresh restore with no valid active track and for adding tracks to an empty playlist (see the next decision) — one consistent fallback target reused everywhere the invariant needs enforcing, rather than a removal-specific "what's next" heuristic. Only when removing the last remaining track does the player still go to its empty state, since there's nothing left to fall back to.

**Always an active track when the playlist is non-empty: one shared fallback (first track, loaded paused) applied at every point the invariant could otherwise break.** Three places can leave the player without an active track if unhandled: a fresh restore whose persisted `activeTrackId` is missing or stale (e.g. that track was removed in another session), adding the first tracks to a playlist that had none active, and removing the currently-active track while others remain (previous decision). All three resolve the same way — `loadTrack(playlist[0], { autoplay: false })` — paused because none of these are an explicit tap on a specific track, matching the existing cold-restore rule already established. This keeps the player from ever presenting a "pick something" dead end when there's already a perfectly good first track sitting right there.

**Reordering mechanism: pointer events driving a drag handle, following the same approach as the waveform's pointer-drag scrub from the prior change.** `pointerdown` on the handle begins tracking; `pointermove` reorders the row's visual position (and, on drop, its `order` value) live; `pointerup` commits the new `order` values for affected rows to storage. One mechanism serves both touch and mouse, avoiding a separate long-press-detection path (which was explicitly decided against during exploration in favor of an always-visible handle).

**Removal gestures: swipe (touch) and a hover-revealed delete control (mouse) as two independent, unconditional paths to the same removal action — no confirmation dialog for either.** Both call the same "remove track" function; there's no shared gesture-classification logic needed here (unlike the waveform's tap-vs-drag disambiguation) since swipe and hover-reveal-then-click are already unambiguous, distinct input patterns that don't compete with each other or with the drag-handle reorder gesture (which requires starting the drag from the handle specifically, not anywhere on the row).

**Adding tracks: `<input type="file" multiple accept="audio/*">` plus a drag-and-drop handler that iterates `e.dataTransfer.files` instead of taking just the first one.** No File System Access API, no persisted directory handle — every add is an explicit, one-time file selection whose bytes get copied into IndexedDB, exactly like today's single-file flow, just for N files instead of one and appending instead of replacing.

**Playlist surface: a modal/overlay opened from the main player screen, not an inline section.** The main screen (waveform, transport, balance/mono/speed) stays focused on whichever track is currently active and doesn't permanently spend vertical space on a list that can grow arbitrarily long. A compact trigger on the main screen (e.g. a "Playlist" button, optionally showing a track count) opens the modal; the modal itself is where the track list, drag-handle reordering, and swipe/hover-reveal removal all live. The "Add to playlist" control (the file-picker trigger) moves inside this modal too, rather than sitting on the main player screen — including for the very first track ever added, so there's one consistent add-affordance rather than a different one for the empty-playlist case versus the steady state. Drag-and-drop of files onto the screen, however, is treated as a screen-wide gesture independent of whether the modal is open — this doesn't contradict the spec's "dragging one or more audio files onto the player screen" wording, and avoids forcing the user to open the modal just to drop a file. Alternative considered: keep the playlist inline beneath the transport controls — rejected per explicit direction; a modal keeps the main screen's layout stable regardless of playlist length. Assumption carried into tasks.md: selecting a track from the modal closes it, returning focus to the main screen showing the newly active track — flagged there for confirmation, not treated as settled (unaddressed by the follow-up round of feedback that added the decisions below).

**Correction: the implementation initially drifted from this decision's own "one consistent add-affordance" goal, and was fixed in a later round.** The first pass ended up with three different empty-state presentations — the modal's empty state as a large dashed-border dropzone card with its own text and hidden input, the modal's non-empty state with a separate compact plus-icon button, and the main screen's empty state with its own "No track selected" message plus a redundant "Open playlist" button (redundant because the header's "Playlist" trigger already opens it). Feedback corrected this: the main screen's empty state is now just "Playlist is empty" with no button (the header trigger is the only way to open the modal from there), and the modal's empty state now shows the same "Playlist is empty" message alongside the *same* plus-icon add button used in the non-empty state — one add control, one wording, regardless of whether the playlist has tracks yet.

**Playlist modal starts open.** The modal's `isPlaylistOpen` state defaults to `true` rather than `false` — the playlist is the primary entry point now that the add-tracks control lives inside it (per the decision above), so opening the player screen straight to an empty main view with no visible way to add a track would be a dead end until the user found the (currently small) header trigger. This is a UI-layout default, not a new behavioral contract: nothing about adding/persisting/selecting/reordering/removing changes, only which container is visible first. Cold-restore of the last-active track (paused, per the decision above) still happens underneath/behind the open modal exactly as before.

**Previous/next track controls repurpose the existing "jump to start"/"jump to end" buttons.** The original single-file player had `SkipBack`/`SkipForward`-icon buttons that jumped to the absolute start/end of the one loaded file — behavior the spec never actually formalized as a requirement (an omission from before this change, not something being modified here). Those icons are the conventional media-player glyphs for "previous/next track," so with a real playlist now in place, they're repurposed to that more natural meaning rather than left as same-track start/end jumps (which have little value once there's a "previous/next track" concept to reach for instead) — a new `getAdjacentTrack(offset)` helper finds the neighboring track by the active track's current index in the (already order-sorted) `playlist` array. "Next" advances to the next track when one exists; with none (the active track is last), it falls back to the original "jump to end" behavior on the current track rather than doing nothing, keeping the button meaningful either way instead of ever being a dead press. "Previous" follows the standard media-player convention: restart the current track if more than `PREV_TRACK_THRESHOLD_SECONDS` (3s) into it, otherwise fall back to the previous track, or to the original "jump to start" behavior if there is no earlier track — so a single previous-tap near the start of a track always reaches the track before it (or the very start of the first track), while a tap mid-track just rewinds to the top of what's already playing (matching what most listeners expect from a "previous" button, and explicitly requested this way). Both fallbacks are symmetric: next-with-nothing-further behaves like the old end-jump, previous-with-nothing-earlier behaves like the old start-jump. The separate ±10-second `Rewind`/`FastForward` buttons are untouched — they still nudge within the current track.

**Auto-advance on natural end reuses the same next-track logic as the manual button.** The `<audio>` element's native `ended` event (not previously handled at all) calls the same function the next-track button calls: if a next track exists, load and autoplay it; if not, its jump-to-end fallback is a harmless no-op since the track is already at its end when `ended` fires. No separate "auto-advance" code path — one function serves the manual and automatic triggers alike. This is deliberately a different trigger from "removing the active track" (which stops and clears the active track outright, per the decision above) — reaching the natural end of a track is not the same event as deleting it, and the spec keeps them as two independent requirements with different outcomes.

**Playlist modal stays mounted at all times; `isOpen` controls a CSS transition instead of conditional rendering.** Conditionally rendering the modal (`{isPlaylistOpen && <PlaylistModal />}`, the original approach) can't animate a close — the element is simply gone on the next render, with no time for a transition to play. Keeping it always mounted and toggling `opacity`/`translate-y` classes (with `pointer-events-none` and `aria-hidden` while closed) lets both open and close animate via a plain CSS `transition`, no animation library needed.

**Reordering animates via a manual FLIP (First-Last-Invert-Play), not a library.** Each row's `getBoundingClientRect()` is recorded in a ref map; when the `tracks` order changes, a `useLayoutEffect` compares old and new rects per row and applies an inverse `translateY` that immediately (no transition) puts the row back where it visually was, then on the next frame clears the transform with `transition: transform 200ms ease` active — so the row animates from its old position to its new one instead of jumping. This covers both a manual drag-and-drop and any other future cause of reordering, since it reacts to the resulting array, not the gesture that produced it.

**Swipe-to-remove row restructured into three stacked layers to reveal a trash icon underneath.** Previously the transform for swipe was applied directly to the `<li>`, which had nothing behind it to reveal. Now each row is: an outer `<li>` (measured by the FLIP effect above, `overflow-hidden`) containing (1) a full-bleed reveal layer (red background, centered trash icon, `aria-hidden`) and (2) a foreground `<div>` — opaque, matching the row's current background — that holds the drag handle, title, and delete button, and is what the swipe pointer handlers actually translate. Sliding the foreground away during a swipe uncovers the reveal layer underneath, making the impending delete obvious before release. The hover-revealed delete button sits `absolute` at the foreground's right edge with the same background color, so it can overlap and blot out the tail of a long truncated title on hover instead of the title needing to reserve space for it. The reveal icon's `justify-content` is set directly (not via a fixed class) on every `pointermove`, based on the sign of the swipe delta — swiping left uncovers the reveal layer's right side first, so the icon justifies right there (and vice versa for swiping right), matching the iOS Mail-style convention of the delete affordance appearing anchored to the edge the row is sliding away from, rather than sitting statically centered regardless of direction.

**Waveform canvas is explicitly cleared on every track load, not just its backing `peaks` state.** `setWaveformPeaks(null)` alone doesn't repaint anything — the draw effect only runs when new peaks arrive, so between tracks the *previous* track's waveform bitmap was left sitting on the canvas, visible behind the transparent "Loading…" placeholder text until the new peaks finished computing. `loadTrack` now also calls `canvas.getContext("2d")?.clearRect(...)` directly alongside resetting the peaks state, so the canvas is genuinely blank the moment a new track starts loading.

**Fixed a dark-mode text-visibility bug on the new playlist's title/close/dismiss buttons, traced to a leftover base-template CSS rule.** `src/index.css`'s `@layer base { button { ...; color: #10141e; ... } }` is Vite's original scaffold styling, still present and still targeting every `<button>` element in the app. Buttons that set their own explicit `color` (inline style, which always wins over any stylesheet rule) were unaffected; the playlist's title, close, and dismiss-error buttons didn't, so they inherited that hardcoded near-black color instead of the theme's `--text`/`--accent` — invisible against the dark-mode panel background (in light mode `--text` happens to equal the same hex value, which is presumably why this was never noticed elsewhere). Fixed narrowly by adding explicit `color: var(--text)` / `var(--accent)` to just these three buttons, matching the pattern already used by the drag-handle and delete buttons. Not fixed at the root (removing the legacy rule from `index.css`) in this change, since that rule likely affects other pre-existing buttons across the app that haven't been reported as broken and weren't otherwise in scope here — worth a follow-up look outside this change if other icon buttons turn out to have the same latent issue in dark mode.

**Fixed a bug where multi-file add on an empty (first-ever-use) playlist silently kept only one file, by memoizing the IndexedDB connection instead of opening it fresh per call.** Every exported function in `playerFile.ts` (`getPlaylist`, `getGlobalState`, `setGlobalState`, `addTracks`, `reorderTracks`, `removeTrack`) called `openDB()` independently, each issuing its own `indexedDB.open(DB_NAME, DB_VERSION)` and never closing it — meaning many concurrent, never-reused connections over the app's lifetime. On a genuinely fresh database (no prior use), the mount-restore effect's `getPlaylist()`/`getGlobalState()` reads and an immediate multi-file `addTracks()` call (itself internally calling `getPlaylist()` again to compute `nextOrder`) could all race to open the same not-yet-created database at nearly the same moment — several concurrent `open()` calls all needing the same `onupgradeneeded` to create the object stores. This is a known source of first-run IndexedDB flakiness, and matched the reported symptom precisely: broken specifically on an empty/fresh playlist, working again "once there's something in the playlist" (i.e., once the database demonstrably exists and every later connection is trivially fast, no upgrade in play). Fix: `openDB()` now memoizes a single shared connection promise at module scope, so every caller awaits the *same* connection instead of racing to open their own — only one real `indexedDB.open()` call ever happens for the lifetime of the page. Not empirically reproduced/confirmed against a live repro (no way to run the dev server from here) — this is the best-evidence diagnosis from reading the code, worth confirming it actually resolves what was seen.

## Risks / Trade-offs

- **[Risk] No eviction means playlist storage can grow without bound, eventually hitting the browser's storage quota.** → Mitigation: per the spec, this is accepted — a friendly message on quota-exceeded (rather than silent data loss) is the extent of handling; the user manages their own playlist size via the removal gesture.
- **[Risk] iOS Safari can clear IndexedDB after ~7 days of inactivity in a non-installed tab (Intelligent Tracking Prevention), which would silently wipe the whole playlist, not just one file as before.** → Mitigation: same underlying risk as today's single-file persistence, just now with more to lose if it happens; worth a soft "Add to Home Screen" nudge somewhere in the UI (installed PWAs are far less subject to this), but this is a UX suggestion, not a functional requirement — noted here rather than in the spec since it doesn't change required behavior, only reduces how often the failure path gets exercised.
- **[Risk] Bulk-adding many/large files at once could exceed available storage partway through.** → Mitigation: per the spec, tracks that already fit remain in the playlist; only the ones that didn't fit are affected, with a clear message — no all-or-nothing rollback of the whole batch.
- **[Risk] Migrating existing users who have a file persisted under the old single-record shape.** → Mitigation: per proposal.md - Impact, no migration is needed; the old record simply becomes orphaned/unused once this ships (small, bounded amount of stale IndexedDB data, not worth writing a migration for a single record).
